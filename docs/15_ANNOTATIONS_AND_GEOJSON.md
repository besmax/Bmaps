# Annotations and GeoJSON

Phase 8 implementation, 2026-09-19. Source and static checks only; builds, automated test execution, application launch, and native acceptance remain with the user.

## Ownership and editing

`domain:map-builder` owns stable annotation IDs, point/line/polygon models, validation rules, the GeoJSON codec, GPX import mapping, and `AnnotationRepository`. `LocalPackageRepository` implements the repository alongside its existing package interfaces, keeping file access, deletion, annotation mutations, and reconciliation under the same operation lock. The umbrella contributes the binding only.

`AnnotationEditorViewModel` owns editing independently of `ViewerViewModel`. `MarkersLayer`, `RouteLayer`, and `PolygonLayer` own kind-specific visibility and selection state. The raster wrapper exposes renderer-independent marker and path overlays; no MapComposeMP types escape `core:map-engine`. The viewer forwards geographic taps and viewport updates to the annotation editor. Overlays are recreated when the renderer changes source level or date-line region and never read tile-network sources.

Long-press the map to open **Map objects**, where you can add a marker, line, or polygon, toggle kind visibility, or select an object in the current viewport. Tapping a rendered marker or path also opens its details. **Edit** changes properties or returns to map drawing. Tap the map to append vertices; markers replace their single coordinate. A draft vertex or its **Move** action chooses a coordinate to replace on the next map tap. The properties dialog also removes individual vertices. **Undo** restores the previous draft snapshot, including vertex additions, moves, removals, color, icon, and text changes; it retains up to 1,000 edits. **Cancel** discards the draft. No writes happen before **Save**. Deletion requires confirmation.

Presentation invokes geometry validation before saving: finite WGS-84 coordinates, one point for markers, at least two nonduplicate adjacent points for lines, and at least three distinct noncollinear vertices with no self-intersections for polygons. Polygon rings are represented without a repeated closing vertex internally. Each object has at most 1,000 vertices, a 120-character name, a 4,000-character description, a `#RRGGBB` color, and a stable icon key. Failed saves retain drafts. Drafts and Undo history survive ordinary ViewModel retention, but are not persisted across process death. Layer visibility and selection are viewer-session preferences.

Selected annotations and imported/recorded routes share `MapObjectCallout` and its immutable presentation display model. Selected objects appear in a map callout with their name, a bounded description, latitude/longitude transformed into the selected display CRS and written in the saved angular format, optional DEM height, and edit/delete actions; only markers expose Move. The ViewModel also rejects whole-object movement for lines and polygons; their vertices remain editable through the existing properties dialog. The callout does not display vertex counts. Placement stays within the visible map layout and uses the clicked point for paths. The coordinate readout uses the actual marker coordinate for markers and the geographic callout click coordinate for lines/polygons; list selection falls back to the first vertex. Saved height is preferred when the readout coordinate matches a stored vertex; otherwise height is sampled at the same readout coordinate and shown as `H: … m` with one decimal only for a finite DEM value. Missing DEM, NoData, outside coverage, errors and pending lookups omit the height row. The card height is bounded to 260 dp and the visible viewport; long content remains scrollable. `RasterMapCallout` attaches the card to MapComposeMP coordinates through the core adapter; the viewer chooses its local offset to keep the card inside the screen. Optional appearance/disappearance animations apply to the card itself and retain its displayed content and anchor throughout dismissal. The native attachment remains until the animation finishes. With `autoDismiss = true`, map gestures dismiss the callout at the initial pointer down, including a drag immediately following object selection; touches inside the card and selecting a destination for an active move remain exempt. Compilation, tests, and device acceptance remain with the user.

Layer managers keep per-object interactions in `AnnotationLayerState.objectStates`, keyed by stable annotation ID. The state includes whether the callout is open, its geographic click coordinate, marker movement, and delete confirmation. Object properties come from the current catalog or viewport snapshot instead of a copied `selected` annotation. The viewer projects the geographic anchor into the active raster pyramid. Opening another card clears earlier interactions; hiding a layer, switching packages, or completing a mutation clears the relevant state, and refreshed data prunes missing IDs. A failed marker move preserves the committed object data and allows retry from its callout. These interaction fields are never persisted. Build and test execution remain with the user.

## SVG marker catalog

Single-marker draft placement grows the chosen icon from zero to full size over 320 ms with eased motion around its fixed geographic tip. Each changed map-tap coordinate advances a session-only `markerPlacementVersion`; `ViewerMapContent` owns the animation and passes draw-phase progress to `MovingMarkerIcon`. Style, text, camera updates and overlay recreation do not restart growth. The viewer hides the redundant vertex overlay for a marker draft, so only its actual icon and color appear; line and polygon vertex controls remain available. Builds, tests and device/emulator acceptance remain with the user.

Selected placemarks (2026-10-11): a saved standard placemark with `objectStates[id].calloutOpen` displays alternating black/white outlines along both its outer silhouette and inner hole. The outer outline uses ten dash pairs and a 1.5-viewport-unit stroke; the inner ring uses four dash pairs and a 1-unit stroke. Both dash phases complete one circuit every five seconds, and selection fades over 160 ms when it changes. Selection uses the existing layer interaction state and is exposed through Compose's selected semantics. Immersive mode hides the highlight; movement uses the existing morph/orbit animation instead. Color, layout size and geographic anchor stay fixed. Both contours, their lengths and dash intervals are prepared once per icon asset; dash phase is read only during drawing and runs only while selected outside movement mode. Source and static checks only; builds, tests and device/emulator acceptance remain with the user.

`feature/viewer/src/commonMain/composeResources/files/markers/place.svg` contains the Material placemark path. `MarkerIcons.entries` maps the stable `place` key to this asset and a localized label. The icon picker is generated from the catalog. Each annotation stores its own color and icon key; color tints the vector at render time, independent of raster-layer opacity.

To add an icon, bundle another SVG and add a `MarkerIconDefinition` plus its label. The bundled SVG subset is deliberately small: a zero-origin numeric `viewBox` and one or more self-closing `<path d="..."/>` elements, using SVG path commands supported by Compose `PathParser`. Flatten transforms and strokes to filled paths before adding an asset. There are no rasterized icon assets, platform SVG libraries, or remote icon requests. Vectors and parsed path nodes are cached together. Unknown saved icon keys render the placemark fallback while retaining the original key for export and future catalog versions.

While `objectStates[id].moving` is true, `MovingMarkerIcon` morphs the standard placemark's cubic contours into a disk, collapsing its inner hole, then separates into three overlapping circles with different radii and opacity. Their centers orbit continuously until movement ends. The transition takes 280 ms and the orbit takes 2.6 seconds. The placemark tip and the orbit center share the geographic anchor in a fixed 48 by 72 dp composable; changing modes never changes the native anchor or layout size. Destination selection and clearing movement reverse the transition while the marker remains rendered. Future icons without the supported placemark contours crossfade to the same orbiting circles. Animation values belong to composition and are read during drawing; frames do not update layer state or register map overlays. Build, runtime animation acceptance, and tests remain with the user.

## SQLite and package recovery

`core:storage` uses the existing version-catalog bundled SQLite driver, independently of `core:mbtiles`. Annotations never enter central Room tables. Each ready package lazily creates `annotations.db` on its first save, with:

- `PRAGMA user_version = 1`;
- `annotation_owner(package_id, updated_at)` to verify package identity and recover modification metadata;
- `annotations(id, feature, west, south, east, north)`, with a primary key and a bounding-box index;
- a complete GeoJSON Feature per row, including user properties, plus indexed geometry bounds.

Version 1 has no predecessor migration. Version 0 is initialized only during explicit creation; unknown versions are rejected without destructive fallback. Connections use no-follow paths, serialized repository access, DELETE journaling, FULL synchronization, and deterministic closure within each operation. Imports and edits use `BEGIN IMMEDIATE` and commit all rows together. Page-count checks occur before commit; failure rolls back the whole batch. The existing package byte limit includes annotations and reserves space for manifest replacement. Physical free-space checks allow for database journaling.

Initial database creation happens in `annotations.db.part`, followed by synchronization and atomic promotion. Recovery removes abandoned creation files and their journal. Subsequent updates commit SQLite first, then atomically replace `config.json` with the database size and modification time, then update Room metadata. A valid package-owned database is authoritative after interruption: opening or reconciliation recovers its hot journal, attaches a newly committed asset if needed, and repairs stale manifest metadata. SQLite integrity is checked when verifying the package; viewport reads do not scan the entire database. No annotation connection survives an operation, so deletion can remove the package without dangling annotation handles.

Viewport queries are inclusive envelope intersections, using SQL filtering and ID-keyset pagination, 200 rows per page. West greater than east denotes a date-line-crossing query and searches both longitude intervals. Degenerate point envelopes are included at boundaries. Results are candidates: an envelope can intersect the viewport even if a line segment or polygon does not. The viewer debounces queries and displays at most 1,000 candidates, with an explicit truncation message. Zooming narrows the query. Both saved geometry and GeoJSON use literal longitude coordinates; segments do not silently wrap to the shortest route across the date line. Create separate objects on each side for a short crossing; multipart cutting is outside this supported subset. Coordinates up to the poles remain stored/exportable; the raster viewport is limited to Web Mercator and clips path latitude to its limit, while points outside that projection are not rendered.

## GeoJSON mapping

The supported interchange subset follows [RFC 7946](https://www.rfc-editor.org/rfc/rfc7946): `Feature` or `FeatureCollection`, with two-dimensional `Point`, `LineString`, and single-ring `Polygon` geometry. Positions use `[longitude, latitude]` in WGS 84 degrees. Closed polygon rings are required on import and supplied on export, with exterior winding normalized counterclockwise (vertex order may reverse while geometry is preserved). Holes, multipart geometry, geometry collections, null geometry, elevation coordinates, and custom CRS declarations are rejected explicitly. Foreign top-level members such as input `bbox` are not retained; bounds are recomputed from geometry.

Feature string IDs map to annotation IDs. Missing IDs are generated. Duplicate IDs within an import are rejected. The UI imports copies with new IDs to avoid overwriting existing objects; a failed import retry reuses its pending IDs. Export preserves saved IDs. Reserved properties are `name`, `description`, `marker-color`, `marker-symbol`, and `bmaps-elevations`; all other JSON properties are retained, including nested values. Unknown icon keys are valid. Colors are RGB hex strings. Input is limited to 4 MB, 1,000 features, and 1,000 vertices per feature; SQLite also caps each serialized feature at 256 KB. Invalid input aborts the complete import.

The Map objects panel provides pasted GeoJSON/GPX import and selectable/copyable GeoJSON export. Export reads all package annotations, independently of viewport and visibility; exceeding the 1,000-feature/4 MB export limit produces an error rather than truncating. Phase 10 adds native file picking into the existing import dialog, GeoJSON file sharing from the export dialog, and complete-package transfer. `MapObjectsViewModel` owns confirmed native/pasted inbound imports; `AnnotationFileViewModel` owns outbound GeoJSON file creation. The editor retains package geometry validation and transactional edits. See `19_PACKAGE_TRANSFER.md`.

## Unified object import and map-owned routes

Map objects presents manually drawn package lines and imported/recorded detailed routes in one Routes section. Start opens the shared start-settings dialog (profile/direction/map-selected start position), then enters the dedicated tracking screen only after actual Start. Full GPX routes belong to the opened package's registered `routes.json` auxiliary asset; an opened map is required for every import. They participate in package size/inventory, export/import and deletion. Frozen activity snapshots and recorded telemetry remain independent.

Native and pasted GPX share explicit summary confirmation in `MapObjectsViewModel`. GPX 1.0/1.1 `trk`/`rte` produce grouped routes with separate segments, source heights/time, names/descriptions and control points; `wpt` produce package markers with names/descriptions and available heights. Waypoint time has no persisted annotation field. No route geometry is simplified or truncated for storage/navigation; adjacent identical coordinates are normalized. Namespace, UTF-8, DTD/entity and complexity checks remain in the domain codec. GPX input keeps its 32 MB/200,000 route-point/100-route/2,000-segment/control/1,000-waypoint bounds. The route asset permits 64 MB and 1,000 routes per package across batches. GeoJSON/package geometry editing keeps its separate 4 MB/1,000-object/1,000-vertex bounds.

Presentation validates both kinds before saving. Prepared IDs remain stable across retry. Route asset and marker writes still have separate commit boundaries: a partial result warns that routes were saved and permits retrying markers without duplicating routes. Cancellation before confirmation saves nothing. `AnnotationFileViewModel` owns outbound package annotation GeoJSON only. The legacy annotation GPX codec remains for its existing domain/editor contracts but has no import UI entry point.

The catalog uses package-filtered Room keyset queries. List paging is separate from map overlays: all route pages for this map are loaded for bounded display previews, without replacing stored geometry. Selected routes are highlighted; list selection fits the map, while a path tap opens the shared map-anchored callout at the clicked coordinate without refitting. List selection anchors it at the first route vertex. The line visibility toggle applies to imported route overlays. The shared callout displays name, description, length, transformed coordinates and available stored/DEM height, with Follow, Edit and Delete icon actions; it has no separate Start/Done row. Imported/recorded route Edit changes name and description with revision-checked persistence, independently validates the full route, and preserves all geometry, segment gaps, control points, heights and timestamps. Their geometry is not converted into the 1,000-vertex annotation editor. Delete requires confirmation, updates map/list selection after success, and deletes only the reusable map route; activity records, samples and frozen snapshots remain independent. Failed saves/deletions retain their dialog and draft/selection for retry. Manual lines retain their existing geometry editor. Legacy application-owned routes can be used from Activities after choosing a target map; the full route is copied into it. Source snapshots are never rewritten by source edits or deletion.

The source map cannot be deleted while its track is recording, paused, interrupted or finalizing. Completed tracks and their snapshots survive package deletion. Archive import validates route geometry and reassigns route ownership to the new map. Activity/route spatial stores remain version 1 and Room remains 4; no migration is added. See [package lifecycle](11_PACKAGE_STORAGE.md), [route transfer](19_PACKAGE_TRANSFER.md#map-owned-route-transfer) and the authoritative [activity/route consistency contract](22_TRACK_MODE_AND_TELEMETRY.md#812-map-owned-route-storage).

## Persisted vertex heights — 2026-10-10

`Annotation.elevations` stores an optional `AnnotationElevation(meters, verticalReference)` per geometry vertex. An empty list represents legacy/all-unknown heights; a nonempty list must match the vertex count and may contain null entries. Values must be finite, with a nonblank vertical reference of at most 64 characters. Zero and negative heights are valid. Each database feature and GeoJSON export writes `properties.bmaps-elevations` as a vertex-aligned array of `{ "meters": ..., "verticalReference": "EGM96" | "EGM2008" }` or `null`; all-unknown objects explicitly write null for every vertex. This optional property keeps geometry positions two-dimensional and retains the actual DEM vertical reference rather than treating orthometric altitude as ellipsoidal height. Polygon export reorders height entries together with the vertices when normalizing winding, without adding a duplicate closing height. Missing properties in old files decode as unknown heights. The SQLite table and package/transfer schema versions are unchanged.

The editor invokes `AnnotationElevationResolver` after independent presentation validation and before transactional saves, marker moves, and confirmed imports. `PackageAnnotationElevationResolver` preserves known heights, fills missing entries from local DEM data, accepts only finite value results and leaves missing/NoData/outside/unsupported/error results null. It uses one short-lived package session per operation and a bounded 2,048-point duplicate-sample cache. Lookup and saving are cancellable until the existing commit boundary; session cleanup runs on cancellation. No DEM is downloaded by this operation. Geometry edits invalidate changed vertex heights, vertex deletion removes the matching height, and Undo restores both geometry and heights. Editing only name/style/text preserves existing heights. Existing objects are not bulk-updated; unknown entries are enriched on their next save when DEM is available.

Marker callouts prefer their stored height, including zero/negative values. Path callouts use stored height when their click coordinate exactly matches a vertex; arbitrary path positions retain the existing DEM lookup. GeoJSON and complete-package transfers preserve stored heights; Unified GPX import preserves waypoint `ele` as `GPX_UNSPECIFIED` height and preserves route elevations in the map-owned detailed route geometry; missing imported marker heights may be filled from the destination package DEM before save.

Verification authored, not run: GeoJSON/stored-feature round trips with null/zero/negative heights, winding/height alignment, legacy unknown heights and malformed height validation; resolver sampling, duplicate points, existing-height preservation, missing data and cancellation/closure; editor invalidation/Undo/resampling; existing native transfer scenario now includes a saved height. Static whitespace/license checks only. Builds, automated execution and native acceptance remain with the owner.


## Callout display CRS correction — 2026-10-11

The callout previously observed only the angular-format preference and formatted the original point explicitly as WGS 84. `CalloutLocationViewModel` now combines the selected point with both saved display CRS and angular format, owns a PROJ transform session, and publishes the transformed coordinate or an explicit error. The renderer anchor, persisted annotation geometry and DEM sampling continue to use the original WGS-84 point. Changing display preferences reprojects the current callout without opening or resampling the DEM package.

A new point or preference clears the previous display coordinate before cancellable transformation. Request versions and point identity prevent an older transform from updating a newer selection. The session closes with the ViewModel. Loading and preference/operation failures are shown explicitly; the UI does not silently format WGS 84 when the selected transformation is unavailable. Geographic CRSs use latitude/longitude rows; the existing EPSG:3857 compatibility preference uses labeled X/Y rows. Dismissal snapshots retain the formatted coordinate and error/loading state.

The viewer center already observes the selected CRS and passes the transformed result into its readout; source review found no equivalent hard-coded WGS-84 formatting there. This does not establish native transformation accuracy or reproduce a device-specific center-readout issue. Added common tests cover live WGS-84/Web-Mercator switching, angular-format changes, unavailable-system handling and selection invalidation without DEM access. Source/resource/license checks only; builds, tests and independent SK-42/PZ-90.11 reference-point/device acceptance remain with the user.

All route callouts use the track glyph in a standard `IconButton` in the same action row as Edit and Delete. The localized Follow accessibility description and busy-state disabling are preserved; route length stays above the divider even when Follow is unavailable. Runtime/device appearance remains unverified; focused verification evidence is maintained in [track-mode status](22_TRACK_MODE_AND_TELEMETRY.md#9-current-state-and-evidence).
